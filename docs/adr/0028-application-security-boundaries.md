# ADR-0028: 애플리케이션 전송·개인정보 경계 강화

- 상태: 채택
- 작성일: 2026-11-13

## Problem 1-Pager

- 배경: apps/web의 인증, 공개 제출, 저장소·문자·관측 전송과 암호화를 코드 기준으로 점검했다.
- 문제: 본문 크기를 Content-Length로만 검사하고, 개인정보 서버 함수·인증 API·완료 화면의 캐시 금지가 빠져 있다. 신청 ID는 열람 권한인데 서버 로그 및 PostHog 이벤트에도 실린다. 오류 원문에는 SQL 파라미터·개인정보가 섞일 수 있다.
- 목표: 실제 본문 바이트 제한, 브라우저 교차 출처 방어 보완, 개인정보 응답의 캐시·리퍼러 차단, 관측 경로의 신청 열람 토큰 제거를 적용한다.
- 비목표: 실제 비밀값·운영 데이터 접근, 배포, 저장소 전면 교체, 신청자 확인 절차의 미승인 변경.
- 제약: 관리자 2단계 인증, 공개 폼 JSON 계약, Google Sheets 원본 및 운영자의 시트 편집 흐름을 유지한다. 재신청 권한 변경은 사용자에게 구체적 영향 설명 후 별도로 결정한다.

## 대안

- 본문 제한 A: Content-Length만 검사한다. 비용은 작지만 헤더가 없는 스트림이나 작은 길이를 선언한 요청을 제한하지 못한다.
- 본문 제한 B: guarded mutation 본문을 상한까지만 읽고 프레임워크에 전달한다(채택). 헤더와 무관하게 제한할 수 있으며, 정상 요청당 최대 1MiB의 버퍼링 비용이 추가된다.
- 개인정보 캐시 A: 개별 서버 함수에 헤더를 붙인다. 공개 응답 캐시를 세밀하게 유지할 수 있지만 인증·개인정보 함수가 추가될 때 누락될 수 있다.
- 개인정보 캐시 B: 서버 함수·인증 API 및 개인정보 화면을 HTTP 경계에서 모두 no-store로 처리한다(채택). 공개 서버 함수의 캐시도 제한되지만 보호 누락을 줄이고 정책을 한곳에서 검토할 수 있다.
- 관측 A: 열람 토큰을 암호화·해시해 계속 보낸다. 이벤트 상관관계는 유지되지만 키 관리나 별도 가명 식별자 정책이 필요하다.
- 관측 B: 열람 토큰 필드를 제거하고 기존 requestId·traceId로 장애를 추적한다(채택). 신청별 분석 속성은 줄어들지만 토큰을 분석 도구나 일반 로그로 보내지 않는다.
- 오류 관측은 원문을 정규식으로 일부 가리는 대신, 오류 종류·코드와 고정된 DB 진단 분류만 허용한다. 원인 사슬은 유지하되 입력값·SQL·파라미터를 전송하지 않는다. 원문 SQL 진단이 줄어드는 비용을 개인정보 보호를 위해 수용한다.
- 브라우저 SDK의 자동 미처리 오류·rejection 수집도 끈다. 명시적인 화면 오류 보고는 원문·cause·stack URL 없이 고정 문장과 오류 종류만 보낸다. 오류 상세 관측이 줄어드는 비용을 수용한다.
- 문자 큐의 새 v2 메시지는 조회 ID·멱등 키·알림 종류까지 본문과 함께 AES-GCM으로 암호화한다. 바깥 필드는 버전·암호문·상관관계 traceId뿐이다. 복호화 후 검증한 문맥으로 멱등 확인·발송·기록을 수행한다.
- 기존 대기 메시지는 발송 손실을 피하려고 이전 형식으로도 읽는다. 기존 메시지의 평문 메타데이터는 새 암호화로 소급 보호되지 않으며 큐가 소진된 뒤 호환 경로 제거를 검토한다. 키는 바꾸지 않는다.

## 영향과 보안 판단

- 변경 경로: 워커 → 요청 정책/본문 제한 → TanStack 서버 함수, 워커 → 개인정보 헤더, 서비스·큐 → 서버 이벤트 카탈로그 → 로거/PostHog.
- 신청 ID는 조회 URL의 bearer capability다. 서비스 반환값·D1·응답 시트·문자 발송에 필요한 ID는 유지하고 일반 로그·제품 분석에서 제거한다.
- 이미 기록된 로그·PostHog 이벤트·이전 큐 데이터는 이 코드 변경으로 지워지지 않는다. 운영 접근 권한과 보존·삭제 정책 및 토큰 교체는 별도 검토가 필요하다.
- 상태 변경 요청에서 Origin뿐 아니라 Sec-Fetch-Site가 cross-site인 경우도 거절한다. Fetch Metadata가 없는 비브라우저 클라이언트는 기존 Origin 검사 계약을 따른다.
- AES-GCM(무작위 96비트 IV), HKDF 용도 분리, HMAC 식별값, 128비트 무작위 신청 ID는 이미 적용돼 있다. Google/SMS의 고정 HTTPS 엔드포인트와 Sheets RAW/명시적 stringValue 사용도 확인했다.
- 응답 시트는 운영자가 읽고 편집해야 하므로 애플리케이션이 답변을 종단간 암호화한 저장소가 아니다. 제공자·공유 사용자 접근 제어와 보존·삭제 정책은 별도로 관리해야 한다.
- 식별값만으로 기존 신청을 갱신하고 조회 링크를 반환하는 흐름은 신청자 권한 확인이 없다. 확인 링크 소유 또는 SMS 인증을 요구하는 제품 흐름 변경이 필요하며 이번 HTTP 경계 수정과 분리해 사용자에게 설명했다.
- CSP의 unsafe-inline 및 암호화 키 교체 절차도 후속 검토 대상으로 기록한다. 이 점검은 운영 TLS·Secrets·Google 공유 권한을 실제 계정에서 확인한 감사가 아니다.

## 검증

- 변경 전에 교차 출처 헤더 누락 방어, 개인정보 응답 헤더, 로그·분석 토큰 유출 및 오류 원문 유출을 회귀 테스트로 재현했다.
- 스트리밍 본문 제한은 Content-Length 미제공·허위 길이·UTF-8 바이트 수·정상 전달·본문 없음으로 검증했다.
- 브라우저 오류의 원문·cause·stack 제외와 SDK 자동 수집 비활성화를 가짜 PostHog 클라이언트로 검증했다.
- 큐 v2는 생산 → 실제 암호화/복호화 → 발송 기록, 잘못된 키 거절, 바깥 메타데이터 조작 무시를 검증했다. 이전 형식의 발송·중복 방지·지원하지 않는 종류 소진 테스트도 유지했다.
- 공개 테스트 설정을 사용한 E2E 25개가 통과했다. 정상 인증 조회의 비저장 헤더, 실제 chunked 초과 요청의 413, Origin 없는 교차 사이트 POST의 403을 포함한다.
- `pnpm check`, 의존성 버전·미사용 코드 검사, 전체 타입 검사와 웹 빌드가 통과했다. 전체 단위 테스트는 498개 중 497개 통과이며 기존 `development-environment.test.ts`의 임시 앱 dotenv 경로 테스트 1개가 실패했다.
- 실제 Sheets·SMS·배포 계정이나 개발용 비밀값은 사용하지 않았다. 신규 큐 형식의 운영 전환은 배포 후 큐 처리 상태를 확인해야 한다.
