# ADR-0016: 모든 화면의 Core Web Vitals 성능 예산

- 상태: 채택
- 작성일: 2026-11-09
- 관련: ADR-0014, ADR-0015
- 기준: https://developers.google.com/search/docs/appearance/core-web-vitals

## Problem 1-Pager

- 배경: 공개 폼의 번들·입력 렌더링은 개선했지만 인증·관리자 화면을 포함한 전 페이지의 LCP·INP·CLS 측정과 회귀 방지가 없다.
- 문제: 단위 테스트와 번들 크기만으로 Google 사용자 경험 기준을 충족한다고 판정할 수 없다. 개발 서버 측정과 인증 리다이렉트도 잘못된 성능 수치를 만들 수 있다.
- 목표: 실제 production SSR을 사용하는 페이지별 모바일 실험실 검사를 만들고, LCP 2,500ms·INP 200ms·CLS 0.1의 예산으로 검증한다. 운영에서는 기존 분석 경계로 실제 사용자 지표를 수집한다.
- 비목표: Lighthouse 점수 100 보장, 모든 기기·회선의 속도 보장, 실제 비밀값 접근, 운영 배포, 검색 노출 허용.
- 제약: 공개 더미 환경과 별도 로컬 D1만 사용한다. 인증을 우회하는 제품 코드를 추가하지 않는다. 개인정보·토큰·입력값을 성능 보고서나 분석 속성에 기록하지 않는다. Effect를 상태 동기화 수단으로 추가하지 않는다.

## 대안

- A: 공개 URL만 Lighthouse로 검사한다. 장점은 표준 보고서이며 단점은 인증 상태와 단계별 화면·상호작용의 누락이다. 위험은 로그인 리다이렉트에 높은 점수를 주는 것이다.
- B: 기존 Playwright에 Google web-vitals를 결합해 production 빌드·실제 서버 인증·단계별 화면을 검사한다(채택). 장점은 모든 화면과 실제 입력을 재현할 수 있다는 것이다. 단점은 fixture·측정 코드가 필요하며, 실험실 INP가 실제 사용자 전체 상호작용을 대표하지 않는 한계를 기록해야 한다.
- 글꼴은 고정 버전 원본을 유지한다. 측정에서 네트워크·글꼴 교체가 병목이면 로컬 제공과 font-display 정책을 비교해 외부 CSS 제거에 이어 개선한다.

## 측정 계약

- 공개 목록·폼·확인·완료·신청 내역, 로그인·가입·전화 인증·2단계 등록·2단계 로그인·비밀번호 재설정, 관리자 목록·관리자 관리·편집·미리보기·응답, 404를 포함한다. 레이아웃 라우트와 API는 화면으로 중복 계산하지 않는다.
- 모바일 viewport, 제한된 네트워크와 CPU, 새 브라우저 context의 cold cache로 production 빌드를 검사한다. 예상 제목·상태·경로와 오류를 검사해 잘못된 리다이렉트·실패 응답을 제외하지 않고 실패로 보고한다.
- 페이지별 여러 표본과 범위를 남긴다. 실험실 결과와 Google의 실제 사용자 75백분위·28일 집계는 별도다. 운영 Core Web Vitals 통과는 실제 사용자 데이터로만 확인한다.
- 인증·신청 내역의 보고서 경로는 고정된 화면 이름을 사용한다. 테스트 세션과 신청 ID는 메모리에서만 전달한다.
- 기존 변경을 유지하고, 확인된 병목만 작은 변경으로 개선한다. 저장 형식·권한·검색 비노출을 유지한다.

## 공통 CSS 영향도와 후보

- CSS는 모든 화면의 첫 paint를 차단한다. preview의 무압축 CSS는 223,965B(gzip 38,297B)이며, 첫 두 화면에서 CSS 종료 시점과 FCP/LCP가 일치했다. 로컬 실험은 무압축 제공이므로 운영 CDN 압축과 차이를 함께 기록한다.
- A: Tailwind 자동 탐색을 끄고 이미 선언된 앱·UI·패턴 `@source`만 유지한다. 장점은 명시한 소스의 클래스가 유지되며 불필요한 문서·테스트 탐색을 막는 것이다. 단점은 새 소비 앱이 자기 소스를 선언해야 하고, 누락된 소스는 스타일 손실 위험이 있다. 기존 세 소스 경로와 E2E로 검증한다.
- B: critical CSS 추출·인라인을 추가한다. 첫 표시에는 유리하지만 화면·상태별 누락과 SSR payload 중복 위험이 커서, 우선 작은 A를 측정한다.

- A를 재빌드한 결과 CSS 바이트가 같았다. 실제 원인이 아니므로 변경을 되돌렸다.
- 실험실 preview는 HTTP 정적 자산을 무압축으로 보내고, 운영 Cloudflare는 압축을 제공한다. 테스트 전용 로컬 proxy에서 `/assets/*.css|js`만 gzip으로 스트리밍해 이 차이를 명시적으로 보정한다. HTML·API·폰트는 바꾸지 않고 CPU 4배·1.6Mbps·150ms·cold cache 조건은 유지한다. 이 결과는 Cloudflare 실측을 대신하지 않으며 무압축 실행과 전후 개선률을 비교하지 않는다.

## 이동 피드백

- 압축 전송을 재현한 1회 기준선에서 신청 내역 → 목록 이동의 INP가 240ms로 예산을 넘었다. 다른 입력은 예산 이내였다. 기준선에는 비동기 로더를 기다릴 때 공통 피드백이 없었다.
- A: router의 isLoading 구독으로 고정 위치 진행 표시를 즉시 그린다(채택). 장점은 모든 화면의 이동에 피드백을 제공하고 본문 위치를 바꾸지 않으며 Effect가 없다는 것이다. 단점은 짧은 이동에도 잠깐 보일 수 있고 실제 로더/렌더 비용 자체를 줄이지는 못한다. 실제 INP 재측정으로 효과를 확인한다.
- B: 모든 링크를 미리 로드한다. 이동에는 유리하지만 모바일 데이터·서버 부하·개인 데이터 요청을 불필요하게 늘리므로 기존 intent preload를 유지한다.
- 영향: 루트에 작고 독립적인 router 구독 컴포넌트만 추가한다. 폼 입력·인증 상태·라우트 로더의 검증은 그대로 두며 성공/실패 이동에서 진행 표시가 해제되는지 E2E로 확인한다.

## 검증 결과

- 17개 화면 × 5회 = 85개 표본에서 측정 실패 없이 예산을 통과했다. 모든 표본에 LCP·INP·CLS가 보고됐으며 개별 표본도 모두 예산 이내였다.
- 페이지별 p75 중 최댓값은 LCP 1,332ms, INP 80ms, CLS 0.0000334944였다. 신청 내역의 이동 INP는 최종 5회 모두 48ms 이하였다.
- 페이지 목록은 모듈 수준 데이터로 두고 필요한 URL만 순수 함수로 치환한다. 경로·권한·상호작용 계약은 유지하며 새 화면 누락을 라우트 목록 대조 테스트로 검출한다.
- `pnpm verify`의 319개 테스트와 기능 E2E 9개가 통과했다. 이동 로더의 성공·실패에서도 고정 진행 표시가 해제된다.
- 운영 Google 통과를 보장하는 수치가 아니다. 메모리 저장소·더미 환경·PostHog 미설정 조건과 1회 기준선의 한계는 [측정 보고서](../performance/pages-2026-11-09.md)에 명시한다.
