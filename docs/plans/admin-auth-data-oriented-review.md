# 관리자 인증 재검증과 데이터 중심 재구성

- 작성일: 2026-11-05
- 상태: 정책·등록 정보·접근 결정·가입 모듈 개선 완료. 요청 제한 정의 공유와 장애 복구 설계는 후속 과제
- 범위: 이메일·비밀번호 로그인, 지정 번호 SMS 확인, 필수 TOTP, 초대·최초 가입
- 관련 결정: [ADR-0009](../adr/0009-admin-sms-verification-and-two-factor.md), [ADR-0010](../adr/0010-admin-auth-deep-modules.md)

## Problem 1-Pager

- 배경: 가입 경로 판단과 요청 보안 규칙은 이미 순수 함수·데이터 표로 분리되어 있다.
- 문제: 런타임 설정의 타입이 실제 바인딩 존재를 보장하지 않아 SMS·관리자 라우트에서 undefined.split이 발생했다. 인증 조건, 표시 문구, 이동 경로도 여러 파일에 분산되어 있다.
- 목표: 검증된 설정과 인증 사실에서 동일한 접근 결정을 파생하고, 서버와 화면이 각자의 역할에서 그 결과를 사용하게 한다.
- 비목표: 인증 엔진 교체, 일반 공개 가입, SMS 로그인, 범용 규칙 엔진, 운영 설정 편집 UI, 인증 상태의 DB 중복 저장.
- 제약: 기존 의존 방향과 보안 보장, D1 트랜잭션 제약, 파일·함수 크기 제한, 비밀값 비노출을 유지한다.

## 이번에 수정한 문제

`ADMIN_PHONES` 또는 `ADMIN_EMAILS`가 런타임에서 누락되면 문자열 분리 중 TypeError가 발생한다.
`runtime.ts`에서 누락을 빈 목록으로 정규화했다. 허용된 이메일 또는 연결된 번호가 없으면 권한·SMS 요청은 거절한다.
로그인 전 설정 조회 자체에서 예외를 던지는 대안은 관리자 라우트도 오류 화면으로 넘어가므로 채택하지 않았다.

이 수정은 누락된 설정을 대신 채우지 않는다. 실제 사용에는 관리자 이메일·지정 번호와 라이브 SMS 설정이 필요하다.
CSP에 차단된 CDN 소스맵 요청은 별도의 개발 도구 경고이며, 이번 수정에서 CSP는 변경하지 않았다.

## 재검증 결과와 한계

| 검증                        | 결과·범위                                                                                                           |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `pnpm verify`               | 포맷·린트·의존성·미사용 검사·타입 검사 및 35개 파일의 테스트 297개 통과                                             |
| `pnpm -C apps/web test:e2e` | 인증 성공/실패, 공개 신청 성공/실패 4개 통과                                                                        |
| `pnpm -C apps/web build`    | 프로덕션 빌드 통과                                                                                                  |
| 설정 누락 회귀              | 이메일·번호 누락, 빈 번호 목록, 미로그인 상태 조회, 인증된 사용자 권한 거절, SMS 미발송 확인                        |
| 인증 계약                   | 실제 Better Auth 처리기와 메모리 저장소, 가짜 SMS 발송기로 만료·오입력·재사용·동시 소비·공개 API 우회 차단 검증     |
| TOTP·복구                   | 등록 전 세션 폐기, 비밀번호만으로 다음 로그인 불가, 복구 코드 일회용, 비밀번호 재설정 후 TOTP 유지 검증             |
| 가입 모듈                   | 실제 가입 인터페이스로 최초·초대 가입, 잘못된 초대·SMS, 가입 실패 후 초대 해제, 기존 계정 차단, 동일 초대 경쟁 검증 |
| SQL 제약                    | SQLite에서 마이그레이션과 최초 관리자 유니크 제약 검증                                                              |

Turbo의 web#typecheck 출력 파일 경고와 vite:css-post의 CSS 소스맵 경고는 남아 있다. 검사·빌드는 성공했다.

검증 범위를 넘는 보장을 주장하지 않는다.

- 성공 인증 E2E는 기존 계정의 SMS 확인·TOTP 등록·로그인이다. 새 관리자의 최초 가입 및 초대 가입 전체 흐름은 포함하지 않는다.
- 메모리 저장소의 동시 OTP 소비·로컬 초대 adapter의 동시 선점 테스트가 운영 D1의 여러 Worker 사이 경쟁을 증명하지는 않는다.
- 최초 관리자 SQL 테스트는 유니크 제약을 확인한다. 두 가입 요청 전체의 동시 실행을 검증하는 테스트는 아니다.
- 초대 선점·OTP 소비·계정 생성 사이의 프로세스 종료나 부분 저장 후 복구는 검증하지 않았다.
- 실제 Solapi 발송·실제 단말 수신, 운영 DB 적용·배포는 수행하지 않았다.

## 대안 비교

| 대안                                                      | 장점                                      | 단점·위험                                                                | 결정        |
| --------------------------------------------------------- | ----------------------------------------- | ------------------------------------------------------------------------ | ----------- |
| 가입 절차를 모듈 내부에 모으고 정책·판단·표시 정의를 공유 | 운영과 테스트가 같은 가입 인터페이스 사용 | 내부 adapter 계약이 필요하며, 원자성·장애 복구는 별도 저장소 설계가 필요 | 채택·구현   |
| DB에 인증 규칙을 저장하고 범용 해석기로 실행              | 배포 없이 정책 변경 가능                  | 수정 권한·정책 버전·캐시·잘못된 조합·실행 순서 관리가 추가됨             | 현재는 보류 |

가정: 운영자가 배포 없이 인증 정책을 편집할 요구는 없으며, Better Auth·Solapi와 현재 관리자 접근 조건을 유지한다.

## 1. 정책은 한 곳에서 정의한다

`domain/admin-auth-policy.ts`에 공개 가능한 타입 있는 정책을 둔다.

- SMS 코드 길이·유효 시간·실패 횟수
- 비밀번호 최소·최대 길이
- TOTP 코드 길이
- 세션·초대 유효 기간

Better Auth 옵션과 입력 스키마는 해당 정의를 사용한다. UI 안내도 공개 가능한 값에서 파생한다.
정책 정의에는 이메일·전화번호 허용 목록, 비밀키, TOTP 비밀, 복구 코드를 포함하지 않는다.
최초·초대 가입 조건은 기존 `decideSignupPath`가, 필수 TOTP는 인증 훅과 접근 판단이 계속 집행한다. 운영 UI에서 TOTP를 해제할 수 있는 옵션은 추가하지 않았다.
인증 엔진의 기본값으로만 보장되는 항목은 실제 적용값과 일치하는지 계약 테스트로 확인한다.

## 2. 설정과 인증 사실을 분리한다

설정은 운영자가 허용한 이메일과 지정 전화번호다. 사실은 인증 엔진과 저장소가 확인한 계정·세션·번호 확인 상태다.
`runtime.ts`만 env를 읽는다. `parseAdminDirectory`는 이메일 허용 목록과 지정 번호를 하나의 등록 정보로 조합하는 순수 파서다. 네트워크·DB 없이 검사한다.

허용 이메일에 없는 전화번호 매핑은 관리자 등록 정보를 만들지 않는다. 허용 이메일에 지정 번호가 없으면 `phoneNumber: null`로 표현하며 관리자 접근과 SMS를 허용하지 않는다. 이메일·번호 형식과 번호 중복을 검증하고 오류에 설정 원문을 포함하지 않는다.
가입자에게는 특정 이메일의 허용 여부를 구분할 수 없는 오류를 유지한다. 현재 설정을 사용하며 전역 권한 캐시는 두지 않는다.

## 3. 접근 결정을 한 번 계산한다

`decideAdminAccess`는 세션 사용자와 등록 정보에서 다음 결과를 반환한다.

```ts
type AdminAccessDecision =
	| { kind: "signed_out" }
	| { kind: "blocked" }
	| { kind: "verify_phone" }
	| { kind: "setup_two_factor" }
	| { kind: "ready"; admin: AdminIdentity };
```

`AdminIdentity`는 domain의 검증된 관리자 식별 정보이며, Better Auth의 원시 사용자 전체를 노출하지 않는다.
공개 결과에는 허용 목록과 지정 번호의 원문을 포함하지 않는다.

- `server/session.ts`: 세션과 현재 설정을 조회하고, 순수 판단 함수를 호출한다.
- `requireAdmin`과 이를 호출하는 `adminOnly`: 매 요청에서 계산한 `ready` 결과만 허용한다.
- 보호 라우트: 관리자와 상태를 각각 조회하지 않고 하나의 결과를 받아 이동한다.
- `model/admin-auth.ts`: 결과 종류별 이동 경로와 정책에서 파생한 코드 입력 속성·안내를 선언한다. 권한 판단은 하지 않는다.

접근 상태를 DB나 브라우저 저장소에 별도의 권한 원본으로 저장하지 않는다.
TOTP 등록 여부와 로그인 시 2단계 인증 완료는 다른 사실이다. 후자는 인증 엔진의 세션 발급 절차가 계속 책임진다.
서버 작업의 허용 여부를 UI 경로 표에서 결정하지 않는다.

## 4. 가입 경로 결정과 실행 완료를 구분한다

현재 `decideSignupPath`의 `invite`는 초대를 검증했다는 뜻이 아니라 초대 경로를 선택했다는 뜻이다.
이 순수 판단은 유지하고, 저장소에서 초대를 원자적으로 선점한 뒤에만 가입 승인을 구성한다.
OTP 소비와 계정 생성도 서버가 명시적인 순서로 수행한다. 클라이언트의 승인 플래그나 실행 명령은 신뢰하지 않는다.

`createAdminSignup`이 초대 선점 → OTP 소비 → 승인 범위 내 계정 생성을 담당하며, 예외가 발생하면 초대를 되돌린다. 운영에서는 D1 adapter를, 테스트에서는 로컬 adapter를 주입해 같은 가입 인터페이스를 사용한다. 가입 테스트가 승인 범위를 직접 열어 실제 가입 절차를 우회하던 경로를 제거했다.

최초·초대 가입 성공과 실패 후 초대 재사용, OTP 소비 이후 비밀번호 검증 실패 시 OTP 재발급 필요성을 테스트로 확인했다. 프로세스 종료 시에는 catch가 실행되지 않을 수 있으므로, 재시도·복구 요구가 생기면 다음을 별도 설계한다.

- 초대 예약 토큰·만료 시각과 가입 완료 정보를 구분한다.
- 예약 해제는 자신이 소유한 예약에만 적용한다.
- 계정 생성 결과가 불명확한 경우 이메일/사용자 식별자로 완료 여부를 확인한다.
- OTP 소비 이후 실패 시 재발급 또는 안전한 재시도의 사용자 경험을 명시한다.

이 내용은 재현된 신규 결함이 아니라 현재 코드와 검증 범위에서 확인한 복구 설계 과제다.
DB 유니크 제약과 조건부 갱신은 계속 유지한다. 순수 판단 함수가 저장소 경쟁을 대신 해결하지 않는다.

## 5. 후속 과제: 요청 제한의 정의 공유

현재 워커 요청 정책과 Better Auth 훅은 공개 전화번호 API·TOTP 해제를 각각 차단한다.
이번에는 기존 집행 지점과 테스트를 유지했다. 후속 변경에서는 중복되는 경로·접근 요구 정의를 공유해 변경 누락을 줄일 수 있다.
`features → platform` 의존 방향에 맞게 공유 정의는 `platform/server/security`에 둔다.
공개 HTTP와 승인된 서버 호출의 차이를 유지하고, 경로 문자열을 모두 범용 명령으로 바꾸지는 않는다.

## 영향도와 실행 순서

| 단계 | 범위                                     | 완료 기준                                                           |
| ---- | ---------------------------------------- | ------------------------------------------------------------------- |
| 1    | `runtime.ts`, 설정 회귀 테스트           | 이번 split 오류 재현 테스트 통과, 누락 시 권한·SMS 차단: 완료       |
| 2    | 신규/초대 가입 및 실패 복구 테스트       | 가입 모듈·로컬 adapter 검증 완료. D1 다중 Worker·장애 복구는 미검증 |
| 3    | 정책 정의, 인증 옵션, 입력 스키마, 안내  | 완료: 기존 적용값 유지, 정책과 UI 안내 일치                         |
| 4    | 접근 판단, 세션, 보호 라우트, UI 경로 표 | 완료: 하나의 서버 결정 사용, 조건 조합·권한·라우트 회귀 검증        |
| 5    | 공통 엔드포인트 제한 정의                | 후속 제안. 기존 공개 API 우회 방지 테스트 통과                      |
| 6    | 필요 시 초대 예약·부분 실패 복구         | 미구현. 장애 주입·동시성 검증과 함께 별도 설계                      |

새 정책 엔진이나 DB 구조부터 만들지 않는다. 기존 모듈의 중복 판단을 줄이고, 각 단계에서 `pnpm verify`와 관련 E2E로 동작을 확인한다.

## 구현 요청문

> 기존 관리자 인증 동작을 보존하면서 데이터 중심으로 점진적으로 리팩터링한다.
> 먼저 신규·초대 가입과 부분 실패의 검증 공백을 줄인다.
> 인증 정책·검증된 설정·인증 사실·접근 결정을 구분하고, 순수 판단 함수가 접근 결정을 반환하게 한다.
> 서버 권한 검사와 화면 이동은 같은 결정 모델을 사용하며, 매 관리자 요청에서 서버가 재평가한다.
> 정책값으로 인증 옵션·검증·안내를 구성하고, 원본 사실에서 계산 가능한 상태는 중복 저장하지 않는다.
> Better Auth·Solapi·현재 DB 제약을 유지하며, 보안 정책 완화와 범용 규칙 엔진 도입은 제외한다.
> 단계별로 기존 성공·실패·우회 방지 테스트를 통과시키고, 검증하지 못한 동시성·복구 범위를 명시한다.
